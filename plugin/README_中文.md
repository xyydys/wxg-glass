# WeChat Liquid Glass · TEST4 FIX105 测试版 ABC

版本 `0.4.105-test4fix105abc`。只改一处行为：**没授权时插件在微信里不留任何痕迹。**

- 以前没授权（含“验证中”“还没读到账号”）只是不加玻璃效果，但插件的 overlay 图层还挂在微信视图树里，悬浮入口在设置入口钩子失败时还会露出来。现在这些状态下 overlay 整个从视图树移走、悬浮入口藏起，**连微信「设置」里那行插件入口也不插入**，微信任何地方都看不出装过插件。授权确认后，下次微信重建设置表格时那行入口会重新出现（一般授权早在你翻到设置页之前就完成了）。
- 已授权账号的玻璃和 FIX104 完全一样，确认授权后 overlay 自动装回来。
- **一个说明：** 被踢但手机里还有有效票据的账号，冷启动会先凭本地票据显示玻璃，等后台联网、服务器回 403 后再撤掉——那一下“闪”是踢人生效的过程，离线优先的授权没法免掉（除非每次冷启动都强制先联网再决定，那样会牺牲离线可用性和启动速度）。真正“从没授权过”的账号不会闪，一开始就是原生。

## 云端编译（GitHub Actions）

本地 `tools/build_deb_linux.sh` 已经不依赖 Theos（直接 clang→lld→ldid→dpkg-deb），所以搬到 GitHub 云端几乎原样跑。源码里已带 `.github/workflows/build.yml`。

**第一步 · 普通包（现在就能用）**

1. 建一个**私有**仓库（源码里有着色器，别用公开仓库），把整个工程推上去。
2. 进仓库 Actions 页，启用工作流。
3. 推 `main`、或打 `v*` 标签、或手动点 Run，就会在 Linux runner 上出 deb：
   - 装 `clang-18`、`lld-18`、`dpkg-dev`；
   - 拉 `theos/sdks` 的 `iPhoneOS16.5.sdk`（带缓存，第一次慢，之后秒过）；
   - 下 `ldid`；
   - 跑 `tools/build_deb_linux.sh`，并校验 dylib 里没有着色器文本。
4. 产物在该次运行的 **Artifacts** 里下载；打 tag 的话还会建一个 Release。
5. **不需要配任何 Secret**：着色器在服务器，deb 里没有秘密；签名是 `ldid -S` 假签，不用苹果证书。

**第二步 · 混淆包（可选，需先备好混淆 clang）**

出包脚本已支持换编译器、只混淆指定文件，环境变量控制、默认关：

- `CC` / `CC_DIR`：混淆版 clang 及其所在目录（不设就是普通 clang-18）；
- `OBF_FLAGS`：`-mllvm` 的混淆开关，例如 `-mllvm -sobf -mllvm -fla -mllvm -sub`；
- `OBF_FILES`：只对这些文件生效，默认建议 `Sources/WXGUnlock.m Sources/WXGLicense.m`（渲染热路径一律不混淆，保帧率）。

接法（二选一）：
- **Docker 镜像**：另写一个 Dockerfile 把 obfuscator-llvm / Arkari 的 clang 编进去，push 到 GHCR；在 workflow 里让 build job 跑在那个镜像里，设 `CC_DIR` 指向镜像内的 clang。
- **CI 内编一次 + 缓存**：加一个前置 job 编混淆 clang，用 `actions/cache` 缓存，后续直接取。

两种都是**一次性把混淆 clang 跑绿**，之后手动 Run 时把 `obfuscate` 选 `true` 即可。`-sobf`（字符串加密）最值：把服务器地址、公钥藏起来。首次务必真机验证，建议先只开 `-sobf`，再逐个加 `-fla`/`-sub`。

## FIX104（测试版 ABC）

版本 `0.4.104-test4fix104abc`。在 FIX103 的联网解锁上改两处：**复查间隔由服务器决定**，**冷启动不再先显示原生界面再跳成玻璃**。

### 这一版

1. **复查间隔由服务器决定（不再是写死的 12 小时）。**
   - 服务器在 200 回答里加 `recheckAfter`（秒），插件按它复查：拿到票据后过了这么久，联网使用时就在后台再问一次。剩不到 3 天时照旧续期。
   - 插件的边界：最少 60 秒一次，最多 7 天（票据有效期）。服务器没给（现在线上的 `worker.js`、FIX103 留下的缓存）时按 **10 分钟**。
   - `recheckAfter` 不在签名里：签名内容还是“授权码|设备|版本|到期时间|摘要”，FIX103 的插件照常能用。它只决定多久复查，改不了签名里的到期时间（断网的被踢账号最多还能用 7 天，和以前一样）。
   - 403 也可以带 `recheckAfter`：没授权的账号多久再来问（插件按 1 分钟到 1 天；没给时 10 分钟）。这样**加人也很快生效**。
   - 这个间隔会一起存进本地加密缓存，重启微信后照样按它来。
   - 结果：从名单删掉一个账号，对方联网使用时最多一个复查间隔就会收到拒绝，插件当场关闭、删掉本地票据。
2. **“重新检测”对已授权账号也会立刻联网。** 以前已授权的账号在设置首页看不到这个按钮，`WXGUnlockStateFor` 的已授权分支也不看 `force`。现在：
   - 设置首页“通用”里多了一张 **“授权”** 卡片（正好补上原来的空位），副标题是“有效至 10月22日 · 点按检测”；
   - 点一下立刻联网（不管冷却和退避），副标题变成“正在联网检测…”，结果出来弹提示：授权有效（新的到期时间）/ 联网检测没有成功（原因，本地授权仍有效）/ 插件需要更新；
   - 如果这个账号已经被移出名单，玻璃当场消失，首页换成“当前微信账号未授权”卡片。
3. **冷启动不再闪。** 原因和你说的一样：本地票据在后台读完后要排队等主线程（主线程这时正忙着微信自己的启动），第一次刷新时授权还是“正在验证”，着色器也要等这之后才开始编译。现在：
   - 插件一加载（构造函数里）就在后台读票据、算设备码，读完**直接在后台把着色器交给 Metal 编译**，不再绕主线程；
   - 第一次判断授权之前，主线程先接手已经读好的票据（还没读完就最多等 0.3 秒，只等这一次；平时读票据只要几毫秒，而且远早于第一次刷新）；
   - 所以第一次刷新就是“已授权”，玻璃视图建好时着色器多半也已编译好。
4. **复查不打扰界面。** 已授权账号现在几分钟就问一次，所以：请求在后台队列组装和发送；续期成功、或者失败但票据还有效（授权没变）时不再刷新整个宿主，只通知设置页；续期日志一小时最多一条。
5. **诊断**（`license.unlock`）：`cacheReadAtMS`（插件加载后多少毫秒读完票据）、`cacheReadMS`、`cacheWaitMS`（主线程等了多久，-1 = 没等）、`ticket.recheckAfterSent` / `ticket.recheckEveryS`。日志里“玻璃着色器已就绪（cache，…，加载后 N ms）”。

## 服务器要改的（还没推送）

线上 `worker.js` 现在不发 `recheckAfter`，插件会按默认 10 分钟。要由服务器决定，在 `wxg-glass` 的 `worker.js` 里加两个常量、两处回答带上它（`ServerPatch_FIX104/worker.js.diff`，8 行）：

```js
const RECHECK_AFTER = 300;          // 已授权账号多久回来问一次（秒）
const DENIED_RECHECK_AFTER = 300;   // 不在名单的账号多久再来问一次（秒）
// 403: { error: "not authorized", recheckAfter: DENIED_RECHECK_AFTER }
// 200: { ver, expiresAt, shader, digest, sig, recheckAfter: RECHECK_AFTER }
```

以后想改间隔，只改这两个数字推送就行。注意：改小以后，每台手机要等它**当前**这一轮间隔到了才会拿到新值。

## FIX103（测试版 ABC）

版本 `0.4.103-test4fix103abc`。从这一版起，**谁能用由服务器决定，玻璃着色器也从服务器来**；插件本身是空壳。

### 插件这一端的联网解锁

1. **插件里没有着色器了。** 编出来的 dylib 里搜不到着色器文本（FIX102 的 dylib 里有）。着色器只在服务器验证通过后下发。
2. **第一次打开**：读到微信账号 → 连接授权服务器 → 验证通过后玻璃自动出现，不用重启微信。验证期间微信保持原样，设置页显示“正在联网验证授权”。
3. **校验**：服务器的回答要同时满足三条才用——着色器的 SHA-256 等于签名里的摘要；签名用插件内置公钥验过（ECDSA P-256，签的是“授权码|设备|版本|到期时间|摘要”）；版本是插件要的第 1 版。任何一条不对都当作失败，不缓存。
4. **本地缓存**：票据加密存在微信自己的目录里（AES-256，密钥和这个账号、这台手机绑定，拷到别的手机解不开，签名里也写着设备）。
   - 7 天内不联网也能用；
   - 联网使用时，拿到票据 12 小时后、或剩不到 3 天时，在后台自动续期；
   - 冷启动时直接从缓存编译着色器，和以前一样快。
5. **踢人 / 加人都在服务器上**：
   - 加人：没授权的账号，设置页会显示它的**授权码**，“复制账号”会把账号和授权码一起复制。把授权码加到 `wxg-glass` 仓库 `worker.js` 的 `ALLOWLIST`、推送，对方点“重新检测”即可。也可以用 `python3 tools/license_hash.py <wxid>` 算。
   - 踢人：从 `ALLOWLIST` 删掉并推送。对方下次续期（联网使用时最多 12 小时）收到拒绝，插件立刻关闭并删掉本地票据。如果对方一直断网，最多用到票据到期（7 天）。
6. **发给服务器的只有两个哈希**：授权码（账号的 SHA-256）和设备码（identifierForVendor 的 SHA-256），不发 wxid 原文。
7. **设置页的状态卡**：正在联网验证 / 连不上授权服务器（附原因）/ 当前账号未授权（账号 + 授权码）/ 插件需要更新。
8. **诊断**：`license.unlock` 里有服务器、票据来源（缓存 / 服务器）、到期时间、请求次数、最后一次状态码和错误、手机时间偏差。

### 要注意的

- **`workers.dev` 在国内很多网络下连不上。** 先找一台不开代理的手机试一次。要是卡在“连不上授权服务器”，给 Worker 绑一个自己的域名（Cloudflare 里 Worker → Settings → Domains & Routes），再把这个地址加到 `Sources/WXGBuildProfile.h` 的 `WXG_UNLOCK_ENDPOINTS` 最前面重新出包；插件会按顺序试。
- **换着色器**：改完 `WXGGlass.metal` 后跑 `python3 tools/embed_shader.py`，再跑 `python3 tools/export_worker_shader.py <wxg-glass/worker.js>`，然后推送 `wxg-glass`。如果 uniform 布局变了，要把 `worker.js` 的 `VER` 和 `Sources/WXGUnlock.m` 的 `WXG_SHADER_VERSION` 一起改。这时旧插件会提示需要更新。
- **源码包里还带着着色器**（`Sources/WXGGlass.metal`、`WXGShaderSource.h`，工具和测试要用），所以只把 deb 发给测试者，源码包不要外传。

## FIX101 为什么更慢了

- 你 FIX101 的诊断里，7 次点按都“等空闲”等了 65–210 ms。可切换之后真正长的只有切换那一帧（100–240 ms，透镜本来就在那一下停住）；之后的慢帧只有 26–83 ms，影响不大。
- 所以等空闲只是让每次都晚开始，换不来多少流畅。这一版**默认关掉**（开关还在）。

## 这一版

1. **插件自己的一个卡顿找到了。**
   - 插件每 3 s 读一次微信账号（授权用，调用微信的联系人管理）。你手机上这一次要 50–95 ms 主线程。
   - FIX101 第一次打开「通讯录」那次，刷新里多出的 57 ms 就是它正好赶上切换；FIX100 聊天返回后那次 94 ms 也在同一步里，很可能也是它。平时它每 3 s 也会跑一次，赶上滑动也会卡一下。
   - 现在改成 60 s 一次，并且只在底栏不动、没在切换、没在推入 / 返回页面时才读；诊断里记了它每次用多久（`accountReadMaxMS`）。
2. **按下就切，不再等两帧**：省掉 30 ms，那两帧本来也看不出变化。
3. **停顿后追上（默认打开）**：微信切页面让透镜停了多久，剩下的动画就快那么久的六成（最多快四分之一），落下的时间尽量和没停时一样。设置 → 底栏 →“图标与动画”→“停顿后加速追上”。
4. **诊断**：每个慢帧多了 `hooksMS`，是插件挂在微信界面里的那些代码（布局钩子、提交前的检查）用的时间。下次能分清慢帧里哪些是微信自己、哪些是插件。

## 还剩下的

- 按下时，微信切页面那一下（100–240 ms，第一次打开某页更长）透镜一定会停住：它和微信用的是同一个主线程，微信原生的标签栏没有动画，所以看不出来。
- “切换页面的时机”里两种取舍可以自己比一比：
  - **按下时**：页面最快，透镜晚 0.1–0.2 s 才开始滑；
  - **落下后**：透镜一按就滑、全程流畅，页面晚约 0.3 s 出来。
- 要两者都要，只能把透镜放到主线程以外去画（大改）。

## FIX101

### 为什么时好时坏

- 看了你 FIX100 的诊断，12 次点按：

  | 情况 | 例子 | 动画用时（计划约 0.47 s） | 最长一帧 |
  |---|---|---|---|
  | 顺 | #4 | 0.54 s | 42 ms |

  | 其它卡的几次（#7、#12 在聊天返回后） | #6、#7、#12 | 0.71–0.96 s | 270–310 ms |

- 卡的不是切换那一下（FIX100 已经让透镜在那一下停住、不跳），而是**切换之后的半秒里**，微信还会接着有 1–4 帧很慢（新页面布局、加载，100–700 ms）。这几帧正好落在透镜滑动的中间，所以透镜走一下、停一下。

### 切换后先等页面忙完，再一口气滑完

- 微信切完页面以后，透镜在原地等（不动，也不变形），直到连续三帧准时（约 50 ms 没有慢帧），然后把剩下的动画按原来的速度完整走完。
- 最多等 0.6 s；超过 0.6 s 时如果刚好还在一个慢帧里，再等到下一帧准时（最多 1.2 s）。
- 效果：滑动本身每次都是最流畅的那种。代价是遇到微信忙的时候，透镜会晚一点开始滑（页面照样马上出来）。
- 设置 → 底栏 →“图标与动画”→**切换后等页面忙完再滑**（默认打开）；关掉就是 FIX100 的边卡边走。

- 每个慢帧多了 `commitMS`：系统把所有界面画出来（布局、绘制）用的时间，用来区分微信页面自己的绘制和其它工作。
- 每次点按（`taps`）多了：

  - `calmWaitMS`：等页面忙完等了多久。

## FIX100

### 为什么原生微信是“秒切”

- 微信每次切标签，主线程都要卡一下。你 FIX99 的诊断里：
  - 「我」57 ms；
  - 「发现」194 ms，之后又忙了约 300 ms；
  - 「通讯录」15 ms，之后约 150 ms（其中插件自己扫页面 36 ms、刷新 49 ms）。
- 原生没有插件时也一样卡，只是：
  - 微信自己的标签栏手指一按下就切；
  - 标签栏本身没有动画；
  - 所以这一下卡在你点下去的瞬间，看起来就是“页面马上出来了”。
- FIX95–FIX99 为了不让透镜卡在半路，让微信等透镜滑到位（或落下）才切。透镜本身也要 0.3–0.4 s，所以页面比原生晚出来这么久，冷启动第一次打开还更晚。
- 两者本来不必冲突，只是顺序反了：应该先让微信卡，再让透镜动。

### 按下时就切换（默认）

- **原因**：原来透镜里底栏变窄，是按“离透镜边多远”算的。透镜两侧很陡，所以在透镜边上收窄成了一个直角台阶，开折射后就被弯成你画的“平底的切圆”。
- **现在**：沿底栏的方向算。从透镜边开始以 45° 斜着收进去，越往里越平，到中间收窄量和原来一样多，折射后接近椭圆。
- **两端照旧正常脱离**：透镜到底栏两端时，端头的圆在透镜里按同样的规则收进去，斜率一路变小，直到和端头一起离开透镜。不会因为 45° 卡住（之前出过的问题）。
- 着色器、系统渲染的透镜、点按动画用的是同一个公式，C 测试里对过。

#### 上下边框“胖回去”

- 我按数值查过折射范围本身：沿透镜轮廓，上下的宽度一直比圆角转弯处窄，没有变宽的地方。
- 所以你看到的“上下比圆角处又胖回去”，我判断是上面那个直角台阶被折射放大出来的那一条，改成 45° 以后应该就没了。另外色散现在有自己的范围（见下面），也会影响上下看起来的粗细。
- 新版里还能看到的话，麻烦截图标一下是哪一条、在什么位置，我再对。

#### 色散有自己的范围

- 像 iOS 26 的透镜：颜色分离不再限在折射范围里。透镜设置里多了两项：

## 页面渐隐偶尔把整页消息隐去

- **现象**（你的截图）：首页往下滑时，渐隐跟着内容一起走，第二行以下全被隐去，只剩底色。
- **原因**：渐隐是挂在列表上的遮罩，坐标跟着列表的滚动位置走，所以每次列表滚动都要把遮罩挪回可见区域。插件靠一张只有 16 格的登记表，从“哪个列表在滚”找到“它的渐隐”。聊天页、插件设置页关掉后，它们的登记从来没被清掉（页面释放时列表已经先没了，清不到）。开过十几个聊天或进过几次插件设置后表就满了，之后每个新列表都写进第 1 格，把最早登记的首页列表挤掉。首页列表滚动时就找不到自己的渐隐，遮罩停在原地，跟着内容滑走，下面的消息就全被遮掉了。所以是“偶尔”出现：用一阵子才会触发，而且一旦出现，首页会一直这样，直到重启微信。
- **修复**：每个列表自己挂着它的渐隐（关联对象，弱引用页面），没有数量上限，列表或页面释放后自动失效。页面每次刷新时再核对一次，万一没关联上就重新关联（诊断里计数）。
- **诊断**：`liveSamplingAtExport.edgeFade` 里每个页面多了 `linked`（列表能找回这个页面）、`maskLag`（遮罩与当前滚动位置的差，正常是 0）、`maskSyncs`（遮罩跟随滚动的次数），以及总的 `relinks`（应该一直是 0）。

- **内侧阴影**：线里面一圈往里慢慢变淡的阴影。浅色、深色各有颜色和浓度，“柔和度”越大越宽越淡。
- 线、阴影都在原来的渐隐遮罩下面，渐隐的地方一起按原来的方式变淡。
- 关掉“描边细节”就是原来的描边。

之前的问题出在哪：

- **不圆、四个点发尖**：新描边的形状是从一张算出来的距离图里取的，不是系统直接画的，正上下左右那几处会有一点误差，看起来就是小尖。现在线条由系统画，和玻璃本身的轮廓完全一致。
- **顶部和底部按钮同样参数效果完全不一样**：新描边的颜色取自每块玻璃后面的背景。顶部按钮后面是页面（或壁纸），输入栏按钮后面是微信输入栏的浅灰底，设置页的卡片干脆没取背景色，所以同一组参数出来的颜色各不一样。你开了“加亮叠加”，浅色背景上很快就加到白；你看到的那圈深色主要是宽度调到 0.5 的内侧阴影。这次没有取背景色这一项了，颜色就是你设的边框颜色。
- **透镜变两条线**：新描边在透镜上又画了一条线（加上一圈很窄的内侧阴影）。现在透镜也只是原来那条边框。

**注意**：测试时你把“其余玻璃”的浅色、深色边框不透明度都调成了 0，装上这版后其余玻璃会看不到描边，需要调回来（原来大约是 0.37 / 0.16）。

## FIX73 的 iOS 26 描边为什么完全没生效

新描边每种形状要先生成两张图（线的透明度图和内侧阴影图），没生成出来之前先显示旧描边。FIX73 生成线那张“只有透明度”的图时用错了 Core Graphics 的创建方式（没给颜色空间），系统直接拒绝，所以每一种形状都失败、被记成失败后不再重试，所有玻璃一直停在旧描边上，调宽度等参数也看不出变化。

现在两张图都改用和工程里其他遮罩一样的方式生成（位图上下文）。另外：

- 形状本身也改用普通的 RGBA 位图来画；万一系统什么都没画出来，就退回用圆角公式算出形状（圆角比系统的连续圆角稍圆一点），不会再整体失败。
- 失败的形状在你改任何设置后会重新尝试，不再永久放弃。
- 导出的诊断里新增 `rims`（在 `liveSamplingAtExport` 下，任何页面导出都有）：每种描边状态的数量（`ios26` 是新描边，`classic` 是旧描边，`ios26_pending` 是还在生成）、生成次数、失败次数和最近一次失败原因、叠加方式、系统是否支持滤色等。新描边如果还不对，导出一次发我就能看到卡在哪一步。

描边宽度用的还是“边框与渐隐”里浅色 / 深色模式各自的“宽度”滑块（底栏范围里另有一套）。

版本 `0.4.64-test4fix64`，只出测试版 A。新增“渐隐与模糊”模块：渐隐用你自己的 WeChatFade 1.1，模糊用另一份工程里的渐变模糊；底栏搜索和 FIX63 完全一样。

## 渐隐与模糊

设置首页“个性化 → 渐隐与模糊”。

- **渐隐**：页面里的主列表在上下边缘变透明。用的是 WeChatFade 1.1 的原样做法：
  - 找列表的方法一样：先看页面的 `m_tableView` / `tableView` 等属性，再在整页里按大小、类型、类名打分挑最大的那个列表；
  - 列表本身挂一层渐变遮罩（129 段，smoothstep 曲线），不加颜色，不盖输入栏；列表原来如果有遮罩，关掉时放回去；
  - 列表滚动、尺寸变化时遮罩跟着走：和 WeChatFade 挂 `MMTableView` 一样，这次挂在找到的那个列表的类上。
  - 和 WeChatFade 不同的地方：不再给每个页面开一个每秒 60 次的计时器反复找列表，改成在页面出现、页面布局（最多每秒一次）和列表丢失时才找；找列表时不进入每一行的单元格。效果相同，开销小很多。
- **模糊**：贴着列表上边和下边各一条模糊带，越靠边越模糊，往里逐渐清晰。用的是那份工程的做法：系统的背景模糊层（半分辨率）加 `variableBlur` 渐变模糊，渐变表就是它里面那张 90 段的表（Telegram 的 EdgeEffect）。
  - 只取了模糊，没有用它的同色色板遮罩，也没有用它的渐隐（渐隐用你的）。
  - 模糊带放在列表的上面一层：在输入栏、导航栏、底栏之下，所以它们不会被模糊，导航按钮和底栏的玻璃看到的是已经模糊、渐隐过的内容。
  - 模糊带跟着列表的位置和大小走；键盘弹出时列表移动的动画，模糊带也一起动。
  - 如果系统没有 `variableBlur`，退回普通模糊加同一张表的渐变遮罩（诊断里会写）。
- **两组设置**：
  - **聊天页**：聊天的消息列表。
  - **其余页面**：首页（聊天列表）、通讯录、朋友圈、聊天设置（单聊和群聊的聊天信息页）；FIX65 起还有微信的“设置”页和本插件的设置页。
  - 每组 6 个滑杆（FIX65）：顶部渐隐距离（0–320 pt）、顶部模糊距离（0–320 pt）、顶部模糊强度（0–8），底部渐隐距离（0–360 pt）、底部模糊距离（0–360 pt）、底部模糊强度（0–8）。强度是最靠边处的模糊半径。距离都从列表的上边、下边往里算，设成 0 就关掉那一边。
  - 默认：渐隐 96 / 112 pt（WeChatFade 的默认值），模糊带同样 96 / 112 pt，强度上下都是 3。
  - 最上面有总开关“页面渐隐与模糊”，关掉后列表和遮罩都恢复原样、模糊带移除。插件总开关关闭时也一样。
- 设置在“恢复本版默认参数”里也会恢复。

## FIX63

版本 `0.4.63-test4fix63`，只出测试版 A。按 FIX62 的反馈：

- **搜索框里看不到词**：FIX62 填入文字后又补了一个换行当作“按搜索”。微信这个搜索框把换行当成了文字，所以显示的是换行后面那一空行，删掉一格（就是那个换行）词才出现。现在只填文字、不再补换行：微信本来就是边输入边出结果，你截图里的结果也正是这样出来的。

- **展开总是左边搜索框、右边关闭**：

- 设置里“搜索时整行宽度比例”的上限改为比平时宽约 64 pt（弹簧和外鼓也要留在画布里）。

## FIX62

按 FIX61 的反馈：

- **输入后直接出搜索结果**（FIX63 起不再补按“搜索”）：FIX61 的诊断显示，微信的搜索页打开、键盘也在时，窗口里找不到获得焦点的输入框（UITextField），所以插件一直等到超时。微信这个搜索页（“搜索本地或网络结果”）的输入框不是普通输入框，很可能是网页里的输入框。现在不再找输入框，而是直接问系统“现在谁接收键盘输入”：只要不是我们自己的搜索框，等它稳定 0.2 秒，就把文字像键盘一样打进去，0.3 秒后再按一次“搜索”键。这样应该直接到你图二那样的结果页。诊断 `lastHandoff` 会写下接收输入的是什么。
- **在其他标签页按搜索不再等一下**：切到“微信”页以后，原来要等插件下一次刷新才去打开搜索；现在每 0.03 秒看一次，“微信”页一出现就打开。
- **从微信搜索页返回后键盘不落下**：原因是系统关闭搜索页时，会把焦点还给打开它之前的输入框，也就是我们底栏里的搜索框，而这时底栏已经复原了。现在底栏搜索框只在展开时允许获得焦点，系统还回来的焦点会被拒绝，键盘就会落下。
- **弹簧时整行微微放大回弹**：原来只有两块玻璃相邻的那两端在伸缩。现在整行外侧的两端也跟着弹簧向外鼓：移动最快时约鼓出整行宽度的 1.4%（宽 368 pt 时约 5 pt），回弹越过终点时再按越过的量鼓出，高度同时增加外扩量的三分之一，停下后完全复原。

## FIX61

按 FIX60 的反馈改了底栏搜索：

- **不自动弹键盘**：点搜索按钮只播放展开动画（搜索框 + ×）。要输入时点一下搜索框，键盘才出来，整行跟着升到键盘上方。
- **搜索时的大小可以调**：“底栏 → 搜索”里新增三个滑杆：
  - **两块玻璃的间距**：2–40 pt，默认 12（FIX60 是按底栏高度算的 11 pt 左右）。平时和搜索时都用它。
  - **搜索时高度（相对底栏）**：0.55–1，默认 0.82。搜索框和 × 一样高，展开时从底栏高度过渡过去，上下居中。
  - **搜索时整行宽度比例**：0.65–0.98，默认 0.94。搜索时这一行可以比平时宽，搜索框更长，但最多比平时宽 72 pt（× 要留在底栏画布里）。
  - FIX60 里搜索框和 × 跟底栏一样高，搜索框和平时的标签栏一样长，而标签栏因为要让出搜索按钮的位置，本来就比 FIX59 短，所以看起来又高又短。
- **文字交给微信搜索**：FIX60 的诊断显示，微信的搜索框开始输入后不到 0.06 秒就不再是焦点（打开搜索页时可能先后聚焦了不止一个输入框），插件当时只试一次就放弃了。现在会一直等到有输入框处于焦点再填入，每 0.1 秒试一次，最多 2.6 秒；到时还没有聚焦的输入框，就直接把文字写进开始编辑的那个输入框，并发出文字变化的通知。另外，开着“隐藏顶部搜索栏”时，原来会在微信搜索框开始编辑的那一刻重设列表表头，可能正是这一步让它失去焦点，现在只取消裁剪，不动表头。
- **灰色闪烁**：FIX60 在标签栏淡出时加了高斯模糊滤镜，这一版去掉了，只保留淡入淡出；搜索按钮在还没有形状时也不再画阴影。没在真机上确认过，所以还不能说这就是原因。如果还会闪，请告诉我是在展开 / 收起动画时，还是键盘出来时；最好录一段屏。

## FIX60：底栏搜索

底栏现在是一整行：标签栏胶囊、一个间隔、一个圆形搜索按钮。

- **玻璃**：搜索按钮用底栏自己的那套玻璃（折射、模糊、材质、边框都跟“底栏”范围的设置），阴影也和底栏一样。
- **宽度**：“底栏宽度比例”现在指整行的宽度，所以标签栏会比 FIX59 窄一个按钮加间距（按钮和底栏一样高，间距默认 12 pt，可调）。觉得挤，就把宽度比例调大一点。
- **左右**：默认在右边，“底栏 → 搜索 → 搜索按钮放在左边”可以换到左边。

### 点一下搜索按钮

1. 按钮像其他玻璃按钮一样按下鼓起，松手后用弹簧展开成搜索框；同时标签栏收成一个圆形的关闭按钮（×）。键盘不会自动弹出。
   - 弹簧参数和你给的 React 代码一样（刚度 230、阻尼 20、质量 1.2），有一点回弹。回弹时变宽的那一边会挤进间隔（最多挤掉 65%），变小的那一边保持圆形，两块玻璃不会重叠。
   - 标签栏里的图标和选中胶囊在前半段淡出（FIX61 起不再加模糊），× 和搜索框里的文字在后半段淡入。
   - 在左边时镜像过来：搜索框从左往右展开，× 在右端。
2. 搜索框是真的输入框：点它弹出键盘，整行跟着键盘的动画升到键盘上方；中文输入、选择、粘贴、清除按钮都和系统输入框一样。
3. 输入后按键盘上的 **“搜索”**，文字交给微信自己的搜索：
   - 插件触发微信原来的搜索入口（首页右上角那个被隐藏的搜索按钮；找不到时用聊天列表顶部的搜索栏），等微信的搜索框开始输入时，把文字像键盘打字一样填进去，所以微信会马上显示这段文字的搜索结果。之后在微信的搜索页里继续操作。
   - 如果当时在“通讯录”“发现”“我”页，会先切到“微信”页再打开搜索。
   - 交接完成后底栏立刻复原（没有收起动画，因为微信的搜索页已经盖上来了）。
4. 点 **×** 退出：键盘收起，搜索框缩回圆形，标签栏展开回来，选中胶囊和图标淡入。

FIX60 的诊断里第一次切页的 `treeScanMS` 已经降到 0.03–0.08 ms（FIX59 是 27–53 ms）。

切页面、弹出设置、打开别的界面时，搜索会直接复原。

### 隐藏聊天列表顶部的搜索栏

“底栏 → 搜索 → 隐藏聊天列表顶部搜索栏”，默认关闭，只在开启底栏搜索时生效。

- 做法是把列表顶部那一块的高度收成 0 并裁掉，列表直接从导航栏下面开始；微信的搜索栏本身还在，微信用它搜索时会临时放回来，用完再收起。
- 只有那一块里只有搜索栏时才会收（多了别的内容就不动，诊断里会写原因）。
- 关掉开关、关掉底栏搜索、关掉插件，都会恢复原样。

## 第一次切到某个标签页时的卡顿

FIX59 的诊断里，第一次切到“我”页时插件的页面扫描用了 52.9 ms，第一次回到“微信”页用了 27.5 ms，之后同样的扫描只要 1 ms 左右。原因是扫描时对每个视图取类名：微信里用 Swift 写的视图，第一次取类名要做一次名字还原（demangle），很慢。

现在这些逐个视图的检查都不再取类名：

- 判断是不是插件自己的视图，改成直接比较类（`WXGIsPluginView`）；
- 找导航栏、聊天列表、消息提示等固定几个微信类时，改成比较类本身；
- 需要按名字匹配的地方（自定义导航栏），先按位置筛掉绝大多数视图，只对顶部那一小块取类名。

结果和原来一样。诊断里的 `treeScanMS` 应该从几十毫秒降到几毫秒；如果第一次切换还卡，导出诊断发我。
