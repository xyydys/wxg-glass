# 琉璃 · WeChat Liquid Glass · TEST4 FIX31

版本 `0.4.31-test4fix31`，基于 FIX30。22 个源文件与 FIX30 逐字节相同（`tools/audit_fix31_scope.py`）。

## 编译错误

`___isPlatformVersionAtLeast` 来自调色盘代码里唯一一处 `@available(iOS 15.0,*)`。这个检查依赖编译器的一个运行时库，手机上的工具链没有链接它。现在改用 `NSProcessInfo` 的系统版本判断，不再需要那个库；全部源码中已经没有 `@available`。

## 底栏切换卡顿

你说得对：卡顿一直存在，FIX27/28 只是让它更重。从数据和代码看，点一次底栏时主线程上有三类工作，而透镜动画本身也跑在主线程上，任何一项卡住，动画就停：

1. **松手那一刻，微信自己切换页面**：同步执行，1–56 ms；切到首页时稳定在 31–46 ms，所有版本都一样。
2. **紧接着，我们的路由刷新**：切到首页时即使在 FIX26 也要 31 ms。FIX30 加了分步计时，具体是哪一步要看下一份诊断。
3. **按下和松开的每一帧**：透镜的大小、放大倍数和折射都随按压变化，所以每帧都要为三个颜色通道各重建一套轮廓网格，再提交给渲染服务。同步模式以来一直如此。

这一版的改动：
- **第 3 项直接去掉**：按压量按 1/32 取整，透镜尺寸按 0.5pt 取整（放大倍数每级差不到 0.7%，肉眼看不出），相邻帧大多用同一套网格；已经算过的网格放进缓存（有字节上限），之后每次点击不再重建。按钮的按压同样处理。
- **第 1 项改为可选**：设置 → 底栏 → 「页面切换时机」：
  - 松手立即（默认，与系统一致）；
  - 透镜到位：透镜滑到目标后再切换，约晚 0.1 秒，滑动过程不会被页面加载卡住；
  - 动画结束：透镜完全落下后再切换，动画最流畅，页面出现最晚。
  等待期间不会把底栏同步回旧的标签；超过 0.6 秒无论如何都会切换。
- **逐帧归因**：从按下底栏到切换后 1.5 秒，每一帧都记账：主线程睡了多久，我们的每帧刷新用了多久（其中底栏、叠加层绘制、背景层设置、网格生成、清理各多少），我们的路由刷新、微信切换各多少，剩下的忙碌时间不是我们的代码，就是微信自己的。最慢的 16 帧记在 `runtime.dockProfile.worst`。

## 请这样测

1. 默认「松手立即」，冷启动后先切一轮四个标签，再来回切几次；
2. 改成「透镜到位」，同样操作，看看哪种手感更好；
3. 导出诊断。看 `dockProfile.worst` 里每一帧的 `otherMS`（微信自己）、`refreshMS`、`tickMS`、`switchMS`，以及 `tabSwitches[].refresh.routeSteps`。

如果最慢的帧里 `otherMS` 占大头，说明主要是微信自己的页面工作，「透镜到位」或「动画结束」是正解。如果我们的某一项占大头，我就针对那一项改。如果主线程空闲、帧间隔却仍然偏长，问题在渲染服务（GPU）这边，下一步就减少底栏的背景层数量。
