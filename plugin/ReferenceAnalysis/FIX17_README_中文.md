# WeChat Liquid Glass · TEST4 FIX17

版本 `0.4.17-test4fix17`，基于 FIX16。本版针对横向大范围转场（例如带壁纸的聊天点进聊天设置）里玻璃背景的拖影／果冻感。光学、模糊、布局、输入、底栏等 21 个源文件与 FIX16 逐字节相同（`tools/audit_fix17_scope.py`）。

## 为什么主线程预算拉满后仍然拖影

预算只决定**多久读一次**，解决不了**读到的是哪一刻**：

- UIKit 的 push／pop、键盘这类系统动画，由渲染服务在**每一帧真正上屏的时刻**计算位置；而玻璃读背景的时刻，比它自己上屏的时刻早 1–2 帧多（读取、GPU、进入合成队列）。转场速度约 1500–2500 pt/s，这 25–50ms 的差就是 25–80pt 的错位。壁纸纹理越强越明显。
- 一次读取要几毫秒，先画的分支和后画的分支，presentation 取值的时刻不同，快速平移时会互相错开，看起来像果冻。

## FIX17 的修改

- **显示时刻预测。** 每张新背景第一次上屏时，记录“开始读取 → 真正上屏”的实际延迟（取平均）。之后每次读取，把每个视图的位置从**它自己被取值的时刻**推算到预计上屏时刻。这样同一张背景里的所有分支对齐到同一时刻，也消除了读取过程中的先后错位。
  - 系统动画中的视图（presentation ≠ model）：按当前速度朝终点（model 值）推算，**绝不越过终点**、也不往反方向推；弹簧回弹段不推算。
  - 滚动等逐帧改 model 的运动（presentation = model）：只补偿“玻璃比内容晚上屏”的那段时间，最多一个观测步长。
  - 手指拖动的交互式返回：只用后一种补偿，因为这时动画由手指驱动，不在渲染服务里按时间走。
  - 玻璃自身的位置用同样方法预测，保证和下面背景的相对关系一致。
- **转场期间放宽预算。** 原生页面转场进行中按“移动”处理（上限 +25 个百分点，最高 85%），尽量每帧都有新读取，避免旧图被拉着走。
- **开关。** 采样设置里新增“显示时刻预测（减少转场拖影）”，默认开，可关闭对比。FIX16 的提交后取样、主线程预算、CPU 路径全部保留。

按 `Tests/MotionPredictionTests.c` 的模拟（414pt、0.35 秒 ease-out push，延迟 16–48ms，60/120Hz）：平均错位 27.7 → 6.1pt，最大 126 → 26pt，且从不越过终点。剩余误差主要在动画刚开始的一两帧（还没有速度历史）。

## 安装

```bash
cd /var/mobile && unzip -o WeChatLiquidGlass_0_4_17_TEST4_FIX17_flat.zip -d WeChatLiquidGlass_FIX17 && cd WeChatLiquidGlass_FIX17 && chmod +x build.sh && ./build.sh rootless
```

rootful 环境把最后的参数换成 `rootful`。替换旧主插件，完全退出再打开微信，确认设置标题为 FIX17。

## 这轮请对照

1. 带壁纸的聊天 → 点进聊天设置 → 返回，分别在预测开／关下看拖影。
2. 手指慢慢右滑返回，再松手；看松手后的收尾动画是否跟手、有无“超前”。
3. 收放键盘；快速甩动滚动后突然停住，看玻璃有没有短暂“冲过头”。

诊断 `backdrop.prediction`：
- `latencyMS`：读取到上屏的实测延迟（60Hz 预计 25–50）；
- `predictedViews`、`maxShiftPt`：最近一次被推算的视图数量和最大推算距离；
- `interactive`、`transition`：当时是否在交互式返回／转场中。

如果看到玻璃内容**超前**于实际内容（尤其是动画收尾或滚动急停），把诊断发回，主要调整的是延迟估计和推算上限。
