# WeChat Liquid Glass · TEST4 FIX19

版本 `0.4.19-test4fix19`，基于 FIX18。本版把背景读取换回 FIX4 的方式，并把读取时刻和上屏方式一起调整。着色器、TEST9 光学、预测模型、布局、输入、底栏等 22 个源文件与 FIX18 逐字节相同（`tools/audit_fix19_scope.py`）。

## “60Hz 采 61 帧”存不存在

不存在。屏幕每秒只产生 60（或 120）个不同的画面状态，比刷新率更快地读，只会读到同一个状态。也没有任何地方存着“下一帧”——下一帧还没被计算出来。

但“读哪一帧”是可以选的，而这正是 FIX4 低延迟的原因：

- **模型树**：微信这一帧正在构建、即将提交的状态。FIX4 读的是它。
- **呈现层 / 渲染服务**：上一次已经提交的状态。FIX15–18 读的是它，又在提交之后才读、才上屏，于是滚动时比内容晚一帧以上。

所以 FIX4 那种“提前一帧”的感觉是真实的，而且这已经是最早的了：读这一帧正在构建的状态，并让玻璃和这一帧一起上屏，就是物理上能做到的极限。

## FIX4 与 FIX15–18 的具体区别

| | FIX4 | FIX15–18 |
| --- | --- | --- |
| 读取对象 | 模型树（本帧即将提交） | 呈现层 / 渲染服务（上一帧） |
| 排除自身玻璃和原生栏 | 临时隐藏这些模型图层，一次 `renderInContext`，提交前恢复 | 逐分支遍历，每个分支单独绘制或原生读取 |
| 读取时刻 | display link 回调里（提交前） | 提交之后 |
| 上屏 | 尽快 | 尽快（提交后才开始，更晚） |
| 系统动画期间 | 画成动画**终点**（FIX4 里图层“冻结”、不对的原因） | 跟随呈现层，但晚 1–3 帧 |
| 开销 | 一次 CPU 光栅 | 多次分支读取 |

FIX4 的低延迟和它的“冻结图层”是同一件事的两面：模型树在滚动、打字时就是当前画面，在转场、键盘这类系统动画期间却是动画结束后的样子。

## FIX19 的做法

1. **默认读模型树（FIX4 方式）。** 和 FIX4 一样：临时隐藏插件自身、排除项、原生导航栏/输入栏和不在玻璃范围内的子树，对整棵模型树做一次 `renderInContext`，在同一个关闭动画的事务里恢复，屏幕上看不到任何变化。读到的结果仍然交给现有的共享图集、GPU 复制、TEST9 模糊和光学。
2. **只在必要时切换到呈现层（FIX18 方式）。** 遍历时检查玻璃范围内的视图，以及玻璃自身的祖先视图：
   - 有系统动画在播放（转场、键盘、插入消息）→ 用呈现层 + 显示时刻预测，这样不会画成终点；
   - 有视频、Metal、毛玻璃等只能由系统合成的内容 → 用呈现层（其中会走原生读取）；
   - 新动画刚出现的一两帧 → 保留上一张背景（这时动画还没提交，读到的会是终点）；
   - 动画结束后自动回到模型树。
3. **在系统提交这一帧之前读取。** 读取从 FIX16–18 的“提交后”挪到“提交前、UIKit 布局之后”，并先完成本帧布局，保证模型树是这一帧的最终状态。
4. **与界面同帧提交。** 玻璃使用 `presentsWithTransaction`，绘制结果和微信这一帧放进同一次提交，一起上屏。所有玻璃共用一次等待，主线程每帧只等一次。
5. **玻璃自身的位置也按同一棵树计算。** 用模型树背景时，玻璃位置也取模型值；用呈现层背景时，取呈现层值（并预测），二者不会错开一帧。

## 安装

```bash
cd /var/mobile && unzip -o WeChatLiquidGlass_0_4_19_TEST4_FIX19_flat.zip -d WeChatLiquidGlass_FIX19 && cd WeChatLiquidGlass_FIX19 && chmod +x build.sh && ./build.sh rootless
```

rootful 环境把最后的参数换成 `rootful`。完全退出再打开微信，确认设置标题为 FIX19。

## 这轮请对照

1. 快速上下滚动聊天和首页：和 FIX4 的跟手程度比较。
2. 带壁纸的聊天进出设置、收放键盘、发送消息：确认不再出现 FIX4 那种“冻结”在终点的图层。
3. 分别关闭“与界面同帧提交”、把采样来源切到“呈现层”，各看一次差别。

诊断里看 `backdrop.regions[]`：
- `lastPath`：最近一次用的是 `modelTree`、`presentationAnimating`、`presentationCompositorContent`、`presentationTransition` 还是 `holdFreshAnimation`；
- `modelReads` / `presentationReads` / `animationHolds`：静止和滚动时应主要是 `modelReads`；
- `runtime.postCommit.presentScheduleWaitMS`：同帧提交时主线程的等待时间，正常应在 1ms 左右。

## 已知风险

- 同帧提交意味着微信这一帧要等玻璃的 GPU 命令排上队才能提交。GPU 很忙时可能拖慢整帧；如果开启后反而卡，请关闭“与界面同帧提交”对比并导出诊断。
- 模型树和 FIX4 一样无法画出视频、毛玻璃等系统合成内容；遇到这些会自动改用呈现层。如果玻璃下面长期有这类内容，那里会一直用呈现层。
- “新动画”是按图层和动画键识别的，最多连续保留两帧上一张背景。
