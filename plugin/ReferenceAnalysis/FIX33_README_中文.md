# WeChat Liquid Glass · TEST4 FIX33

## 卡顿的真正原因（来自你的两份诊断）

逐帧归因的结论很明确：最慢的帧里，我们自己的代码只占几毫秒。每帧刷新 1–3 ms，其中底栏、叠加层、背景层、网格加起来；路由刷新 1–5 ms。慢帧几乎全是微信自己的主线程工作：
- 微信的切换调用：20–166 ms；
- 切换后微信继续忙：100–600 ms，最长持续到点击后约 1.5 秒；
- 甚至手指还按着时也有 110–200 ms，那是微信还在处理上一次点击。

我们的透镜动画原来是主线程逐帧计算的，所以微信一忙它就停。两种切换时机都一样卡，原因就在这里。你的 SwiftUI 工程流畅，是因为系统动画跑在渲染服务里（一个独立进程），不受应用主线程影响。

## FIX33：点击动画交给渲染服务

动画参数是从你的录屏里逐帧量出来的：
- 按下：当前胶囊原地浮起成透镜（约 40 ms），不再一按下就滑向手指；
- 松手：透镜以一个略欠阻尼的弹簧滑向目标，约 0.2 秒到达，有轻微过冲；
- 落下：透镜缩回成胶囊，宽度先压扁到约 86% 再回弹；
- 透镜里的图标放大并显示为选中色（绿色），和录屏一致；
- 拖动仍然跟手，手指移动超过 10pt 才算拖动。

实现方式：松手的那一刻，底栏本身先停在目标位置、隐藏自己的透镜，并立即画一帧不带胶囊的叠加层；同时用一组 Core Animation 图层（毛玻璃底、着色、边框、放大的选中图标）组成透镜，加上弹簧和关键帧动画。然后**先把动画提交给渲染服务，再让微信切换页面**。之后微信卡多久，动画都照常播放。动画结束后，底栏在同一次提交里接回：透镜回到目标位置，胶囊重新出现，动画图层移除。

设置第一组新增开关「底栏点击动画由系统渲染」（默认开），关闭即恢复原来的逐帧动画，方便对比。「底栏切换页面」时机仍然保留；新动画下建议用默认的「松手」。

## 冷启动：底栏没有图标和胶囊、加号按钮没有玻璃

原因：同步模式下，玻璃一激活就被当成“已显示”，于是底栏自带的备用图标、透镜和底板都隐藏了。可冷启动时微信占着主线程，我们的第一帧叠加层迟迟画不出来，看到的就是一条光秃秃的毛玻璃。另外，着色器管线编译完成之前，玻璃整个是隐藏的，所以加号按钮没有玻璃。

现在：
- 只有真正画出第一帧叠加层，才算“已显示”；在那之前，底栏的备用图标和透镜保持可见；
- 背景层不需要 Metal，所以在着色器就绪之前就先挂上，按钮和底栏一开始就有材质，图标、描边稍后补上；
- 同步模式下不再显示底栏的备用毛玻璃底板，避免和真玻璃叠两层。
